# Screening database contract

Use the database selected by `[workflow].database` as the durable project-level screening database. It stores every paper's journal, title, abstract, current screening decision, Chinese reason, model, and downstream states. A separate screening profile row stores the full `criteria` and `decision_prompt` once; never duplicate the prompt on paper rows.

## Import and reuse

Always import candidate files through `autopaper.workflow`; never ask the main Agent to read or compare the complete CSV/JSONL. The importer uses the normalized full journal name plus normalized title as the cross-search identity, with DOI/OpenAlex identifiers as a fallback. It updates metadata without overwriting a valid stored screening result.

Default behavior is reuse:

1. Verify that the selected database's stored screening profile matches the configured criteria and decision prompt.
2. Import the complete current candidate file programmatically.
3. Reuse stored decisions for matching papers and mark them as reused for the current run.
4. For any remaining paper whose abstract is null, blank, or whitespace, store an `uncertain` screening result with model `rule:missing-abstract` and the fixed Chinese reason. Include it in reviews but never in a Sub Agent payload.
5. Render completed results into the current review programmatically, report only compact counts, and send only still-pending papers with usable abstracts to Sub Agents.

Use `import --no-reuse` only on an explicit user request. It resets current matching papers to pending while retaining prior results in the history table; the importer immediately resolves missing-abstract papers back to automatic `uncertain`, so only papers with usable abstracts are screened again.

## Prompt isolation

One physical database is bound to one screening profile. If the configured prompt fingerprint differs from the stored profile, do not reuse or overwrite it. If more than one database/profile could apply, present only compact profile metadata and ask the user which one to use. Never load full stored prompts or paper records merely to make this choice. A genuinely new prompt should normally use a separate database path in `[workflow]`.

## Current-run scope and reporting

SQLite stores the active imported candidate file. Pending-task queries and the mutable current `review.md` are scoped to that active run, while `STATUS.md` remains the project-level aggregate. After the current run has no pending papers, use `finalize-screening`; it generates the reports and saves a separate UTC-timestamped snapshot under `[workflow].review_archive_dir`. Historical review files are immutable task records and must not be overwritten by later imports or renders. All review content and counts are generated by the workflow program; the main Agent reads only compact counts and gives the archived file to the user.

Project review policy: `[workflow].review_include_excluded = true` must be preserved in project and run-specific configurations. Formal and interim reviews expand all completed include, uncertain, and exclude results with original titles, abstracts, and stored reasons. Missing abstracts are labeled; pending papers remain pending and are counted separately. A user may explicitly request correction of a specific historical review.
